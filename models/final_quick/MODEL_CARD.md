# Model card: EMBER2024 Win64 malware detector (QUICK smoke run: tiny data, not results)

Generated by `scripts/export_model.py` (`app/model_card.py`) from `models/final_quick/schema.json` and the tables in
`reports/tables/`. Every measured number (metrics, counts, file sizes) is read from a generated file or measured
from the files, not typed by hand; re-run `run_all.py --steps deploy` to refresh it.

## Model details

* **Version:** `lgbm-random-074e028d112d`; file `models/final_quick/model.txt`, sha256 `074e028d112d01d3241399b8549aa9e2eeffdabf821071b47df7d3b41865f8a0`.
* **Type:** LightGBM gradient-boosted trees, binary objective, 479 trees, LightGBM 4.7.0, seed 42.
  Hyperparameters (found by the `random` search in Step 2): num_leaves=70, learning_rate=0.04401, min_child_samples=46, feature_fraction=0.3976, bagging_fraction=0.6461, lambda_l2=1.983e-05.
* **Input:** the 2,568-value thrember feature vector of a PE file, in 12 groups: general (7), histogram (256), byteentropy (256), strings (177), header (74), section (224), imports (1282), exports (129), datadirectories (34), richheader (33), authenticode (8), pefilewarnings (88).
  thrember commit `0ef753e81d98bf209f71b03cd331dfc190b5b54d`; `signify==0.8.1` (thrember needs this older signify).
* **Preprocessing:** none: the model reads the raw float32 thrember vector; tree splits do not need scaling, so no scaler is shipped. Inference is self-contained: model.txt plus `lightgbm`
  (and thrember to vectorise a raw file).
* **Output:** P(malicious) in [0, 1], a label at the threshold below, and on request the file's top TreeSHAP contributions.
* **Serving:** `app/api.py` (FastAPI: `/health`, `/predict`, `/predict_batch`, `/predict_file`) and `app/streamlit_app.py`; see `DEMO.md`.
* **Export check:** the exported file reproduces the saved Step 2 test_future scores on all
  2,000 rows, max abs difference 0.0e+00; `tests/test_api.py`
  checks the API against offline `booster.predict` to 1e-6.
* **Author:** Isaac Benjamin David (URK23AI1035), IA-3 Part B course project.

## Why this model

Candidates on test_future (weeks 52-63), from `reports/tables/automl_vs_manual_quick.csv` (95% bootstrap CIs):

| model | TPR at 1% FPR | ROC-AUC | interpretability |
|---|---|---|---|
| flaml | 87.9% [84.8%, 91.6%] | 0.9905 [0.9860, 0.9939] | single lgbm model (tree model: native importances and TreeSHAP) |
| autogluon | 90.1% [87.2%, 93.2%] | 0.9923 [0.9888, 0.9951] | weighted ensemble with all weight on LightGBMXT, i.e. one model; it can be explained like any single model of that type |
| h2o | 89.0% [80.9%, 91.2%] | 0.9891 [0.9848, 0.9927] | stacked ensemble: GLM metalearner over 2 of 3 base models (GBM_1, DRF_1); variable importance only for single base models |
| lgbm_tuned | 90.0% [86.0%, 94.2%] | 0.9924 [0.9889, 0.9954] | single LightGBM model (479 trees): native importances and TreeSHAP |
| lgbm_default | 90.1% [86.0%, 94.1%] | 0.9916 [0.9879, 0.9948] | single LightGBM model: native importances and TreeSHAP |
| logreg | 45.7% [27.5%, 59.6%] | 0.7599 [0.7335, 0.7858] | linear model on standardized features: one coefficient per feature |

The deployed model is the Step 2 tuned LightGBM (`random`, the tuner Step 2 selected by CV AUC on train).
Its TPR at 1% FPR on test_future is 90.0% [86.0%, 94.2%]; the strongest other
candidate, autogluon, reaches 90.1% [87.2%, 93.2%]. The paired bootstrap (autogluon minus lgbm_tuned, `automl_pairwise_quick.csv`) gives 0.10% [-2.62%, 2.85%], i.e. no significant difference at 95%.
With detection this close, the tie is broken by what matters in deployment:

* **Interpretability:** one LightGBM booster, so TreeSHAP gives exact per-file explanations (the API returns
  them) and the Step 4 SHAP analysis (`reports/explainability.md`) describes exactly this model.
* **Inference simplicity:** one 3.9 MB text file and the `lightgbm` package. No Java runtime (H2O),
  no 93.8 MB predictor folder (AutoGluon), no preprocessing pipeline, no scaler.
* **A threshold fitted for it:** `models/threshold.json` was chosen on this model's train out-of-fold scores.

The model was fixed in Step 2 and is not retrained here; test_future only confirms that no candidate is
clearly better. Nothing about the model or its threshold was tuned on a test set.

## Intended use

* Triage aid for static analysis of Win64 PE files: rank and flag files for a human analyst to review.
* Research and teaching: comparing manual tuning with AutoML, and studying temporal drift on EMBER2024.

## Out-of-scope uses

* **The sole verdict for blocking, quarantining or deleting files.** The threshold trades many false alarms for few misses.
* **Non-Win64 inputs:** 32-bit PE, .NET-only analysis, scripts, documents, ELF or Mach-O files.
* **Adversarial settings** where an attacker can probe the model or knows its features; robustness was never tested.
* Judging software, vendors or users: a flag is a statistical score, not evidence of intent.

## Training data

* EMBER2024 (thrember), Win64 PE files, weekly releases: trained on the 'train' split: files from weeks 0-51, deduplicated by sha256, stratified by label x week, classes about 50/50 by construction. test_random is held out from the same weeks; test_future is weeks 52-63, strictly later.
* train: 8,000 files, 52 weeks, 2023-09-24 to 2024-09-21,
  49.98% malicious.
* test_random: 2,000 files from the same weeks; test_future: 2,000 files,
  2024-09-22 to 2024-12-14. Source: `data/splits/splits_info_quick.json`.
* Labels are EMBER2024's AV-derived labels (label -1, unlabelled, dropped). Raw weekly files list every sample twice;
  the data was deduplicated by sha256 before any split.

## Threshold and cost ratio

The API labels a file malicious when P(malicious) >= **0.00485527** (`models/threshold_quick.json`).
How it was chosen: minimises C_FN*FN + C_FP*FP over every distinct score on TRAIN out-of-fold predictions (persisted 3-fold CV of the train split, data/splits/cv_fold_ids; tuned params, fixed 479 rounds as the refit); cut placed midway to the next lower score. No test set was used. The cost ratio is 10: a missed malware file
is assumed to cost 10 times a false alarm. From `reports/tables/threshold_quick.csv`
(cost ratio, the threshold chosen on train OOF scores, then the check on test_future):

| cost ratio FN:FP | threshold | OOF recall | OOF FPR | test_future recall | test_future FPR | test_future precision |
|---|---|---|---|---|---|---|
| 1 | 0.2307 | 96.72% | 4.95% | 96.50% | 3.60% | 96.40% |
| 5 | 0.02601 | 98.27% | 9.32% | 97.90% | 7.59% | 92.79% |
| 10 | 0.004855 | 99.00% | 14.37% | 98.90% | 12.99% | 88.37% |
| 50 | 0.0004407 | 99.65% | 27.89% | 99.40% | 23.38% | 80.93% |

At the deployed ratio the threshold is very low, so the model flags 13.0% of benign test_future
files while missing 1.10% of malware. This suits triage (an analyst reviews every flag),
not blocking. For a 1%-FPR operating point use the train-OOF 1%-FPR threshold 0.9743 (rows `train_oof_1pct_fpr`
in the precision table above). Classes are 50/50 by construction; re-derive the threshold for a deployment with another prevalence.

The test_future FPR at the deployed ratio (12.99%) is above its OOF FPR (14.37%):
the threshold was fitted on out-of-fold scores of fold models trained on two thirds of train, while the deployed model
is trained on all of it, and test_future is also later in time (drift). Both are stated in `reports/limitations.md`,
not corrected.

## Calibration

From `reports/tables/calibration_quick.csv` (test_future; calibrators fitted on train out-of-fold scores):

| model | Brier [95% CI] | Brier minus raw [95% CI] | ECE | log loss |
|---|---|---|---|---|
| lgbm_tuned | 0.0299 [0.0239, 0.0365] | - | 0.0236 | 0.1388 |
| lgbm_tuned+isotonic | 0.0283 [0.0234, 0.0335] | -0.0016 [-0.0035, -0.0000] | 0.0121 | 0.1021 |
| lgbm_tuned+platt | 0.0280 [0.0231, 0.0331] | -0.0018 [-0.0034, -0.0004] | 0.0126 | 0.1026 |

The served score is the raw LightGBM probability. Platt or isotonic scaling improves calibration a little
(lower Brier, ECE and log loss above). Platt scaling is monotone, so it cannot change the ranking of files or
ROC-AUC and TPR at 1% FPR (isotonic scaling only adds ties). It is not shipped, to keep inference to one artefact whose threshold was fitted on the raw
score; a calibrated variant would need its own threshold. Either way, the score
is calibrated for a 50/50 class mix only: at another prevalence, read P(malicious) as a ranking score and use
the precision table above, not as the probability that this file is malware.

## Known limits

Measured at the deployed threshold on test_future (`reports/tables/bias_slices_quick.csv`), with the full list in
`reports/limitations.md` and `reports/critical_eval.md`:

* **Signed malware is missed more often:** TPR 83.7% for signed malware vs 99.6% unsigned. Benign
  FPR is 4.8% for signed and 22.1% for unsigned files: unsigned benign software is flagged a lot.
* **High-entropy (packed-looking) files:** benign FPR 18.3% for whole-file entropy > 7 vs 12.4% otherwise.
* **Time proxies inside the features:** the model leans on time-like columns (mean-|SHAP| ranks in
  `time_proxy_ranks_quick.csv`: `header: coff.timestamp` rank 15, `authenticode: latest_signing_time` rank 3, `authenticode: signing_time_diff` rank 4). They are part of the static file, not leaked metadata, but they
  tie the model to its training period. The leaky metadata (`detection_ratio`, `first_submission_date`) is not an input.
* **Benign system files can score near the threshold:** in the demo, Windows' notepad.exe is labelled benign but
  with a score just under the low threshold (one file observed on the demo laptop's Windows build, see
  `reports/screenshots/c_upload_notepad.png`; another Windows version ships a different notepad.exe).
* **Static features only; evasion untested:** appended bytes, added imports or sections, or a valid signature change
  the features without changing behaviour. No adversarial robustness is claimed.
* **Win64 PE only, data up to 2024-12:** other file types, 32-bit PE and newer malware are out of distribution. The API
  warns when a file's machine type is not AMD64, and rejects files that do not parse as PE.
* **Labels come from antivirus verdicts,** and files with an ambiguous number of detections are not in the data
  (`reports/limitations.md`), so the task is easier than real triage.

## Ethical considerations

* **False positives have a cost:** flagging legitimate (often small-vendor, unsigned) software can harm its authors and
  users; the slices above show unsigned benign files are flagged far more often. Keep a human in the loop.
* **False negatives give false comfort:** a "benign" verdict is not a clean bill of health, especially for signed or
  novel malware (challenge set).
* **Dual use:** the SHAP output shows which static features push a score down, which could guide evasion. The API is
  meant for local or authenticated use, not as a public oracle. Its 32 MB JSON-body cap is checked against the
  declared Content-Length only, so a chunked request without one is parsed in full: another reason to keep it private.
* **Uploads:** the API parses uploads in memory and never executes or stores them; the demo uploads only benign
  system binaries. Do not upload files you are not allowed to share.
* **Data:** EMBER2024 contains features and metadata of real malware and benign software, not the binaries; no personal
  data is used.

## How to reproduce

```bash
.venv/Scripts/python.exe run_all.py --steps deploy      # Linux: .venv/bin/python; export + API tests
.venv/Scripts/python.exe -m uvicorn app.api:app --port 8000
.venv/Scripts/python.exe -m streamlit run app/streamlit_app.py
```

The model itself comes from Step 2 (`run_all.py --steps tune`) and the threshold from Step 4 (`--steps eval`);
the whole pipeline is `run_all.py` (seed 42). `DEMO.md` has the full demo script.
