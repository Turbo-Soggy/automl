* **AutoGluon** (WeightedEnsemble_L2): AUC on test_random 0.9929 -> 1.0000, on test_future 0.9923 -> 1.0000; TPR@1%FPR 1.0000 / 1.0000. The leak column ranks #1 by its own importance (100.0% of the total) and #1 by SHAP (99.4%); it kept the column; log lines naming it: 0, warning lines: 0.
* **H2O** (StackedEnsemble_BestOfFamily_1_AutoML_1_20261029_85420): AUC on test_random 0.9784 -> 1.0000, on test_future 0.9802 -> 1.0000; TPR@1%FPR 1.0000 / 1.0000. The leak column ranks #1 by its own importance (80.7% of the total) and #1 by SHAP (65.4%); it kept the column; log lines naming it: 0, warning lines: 5.

**4 of 4 models fell for the leak**: they kept the column and ranked it first (rule: rank 1 by the tool's own importance or by SHAP). No tool can know from the data alone that this column is post-hoc: a column with AUC 1.0 against the label looks like the best feature there is, and every tool's job is to find exactly such features.

Note what temporal validation does **not** show here: the detection ratio of a future file is just as post-hoc as that of a past one, so the leaky models score 1.0000 to 1.0000 AUC on test_future too: the future split cannot expose this leak. Only asking *when would this value be known?* exposes it: a detector scores a file when it first appears, before (or instead of) the antivirus scan the ratio comes from.

## Leak 2: raw `first_submission_date` (a time stamp, not a file property)

`train` dates run from 2023-09-24 00:31:50 to 2024-09-21 22:43:43; test_future dates from 2024-09-22 01:34:18 to 2024-12-14 23:11:37. Every future date is outside the training range. Classes are 50/50 in every week by construction, so the date alone carries almost no label information; any gain must come from combining it with other columns.

* **tuned LightGBM**: on test_random the date did not measurably change AUC (+0.0000 [-0.0007, +0.0007]) and did not measurably change TPR@1%FPR (-0.0170 [-0.0345, +0.0312]); on test_future it did not measurably change AUC (-0.0004 [-0.0010, +0.0002]) and did not measurably change TPR@1%FPR (-0.0070 [-0.0198, +0.0138]). Leak rank #62 (own) / #19 (SHAP).
* **FLAML**: on test_random the date did not measurably change AUC (+0.0006 [-0.0007, +0.0020]) and did not measurably change TPR@1%FPR (+0.0120 [-0.0091, +0.0376]); on test_future it did not measurably change AUC (-0.0001 [-0.0013, +0.0009]) and did not measurably change TPR@1%FPR (+0.0080 [-0.0319, +0.0219]). Leak rank #30 (own) / #38 (SHAP).
* **AutoGluon**: on test_random the date did not measurably change AUC (+0.0001 [-0.0004, +0.0006]) and did not measurably change TPR@1%FPR (+0.0060 [-0.0102, +0.0290]); on test_future it did not measurably change AUC (-0.0002 [-0.0011, +0.0004]) and did not measurably change TPR@1%FPR (-0.0010 [-0.0089, +0.0277]). Leak rank #762 (own) / #21 (SHAP).
* **H2O**: on test_random the date did not measurably change AUC (+0.0011 [-0.0005, +0.0027]) and did not measurably change TPR@1%FPR (+0.0289 [-0.0627, +0.0765]); on test_future it did not measurably change AUC (-0.0005 [-0.0018, +0.0008]) and did not measurably change TPR@1%FPR (-0.0110 [-0.0743, +0.0244]). Leak rank #240 (own) / #239 (SHAP).

What the date can and cannot do on test_future, shown on the tuned LightGBM: the model splits on the date 159 times, and its largest threshold is 2024-09-17 18:40:00. That is before the first test_future date, so all future rows take the same branch at every date split: for this model the column is a constant on test_future. The model cannot tell one future file from another by date; on the date column it treats every future file like the training files submitted after 2024-09-17 18:40:00.
Whatever the date did on the random split, it carries no information to test_future.

No model got a measurable AUC gain from the date, even on the random split (every paired CI includes 0 or is negative). With 50/50 classes in every week the raw date is a weak leak in this dataset; it would be a strong one wherever the share of malware changes over time.

Located in thrember's source (`process_raw_features()` of each class lists the values in vector order; `src.leakage.time_proxy_provenance()` re-reads the source and checks each position):

| Column | Name | thrember class | Value | Meaning | Source (method start) | Position verified |
|---|---|---|---|---|---|---|
| 696 | `header__0` | HeaderFileInfo | `raw_obj["coff"]["timestamp"]` | COFF header TimeDateStamp (the linker's build time), unix seconds | features.py:773 | yes |
| 2478 | `authenticode__6` | AuthenticodeSignature | `raw_obj["latest_signing_time"]` | latest countersignature signing time, unix seconds (0 when unsigned) | features.py:972 | yes |

The other authenticode columns (2472-2477: certificate count, self-signed, empty program name, no countersigner, parse error, chain depth) and the rest of the header block are not times.

|---|---|---|---|
| tuned LightGBM | #61 / #50 | #4 / #4 | #6 / #3 |

| H2O | #2518 / #2511 | #3 / #2 | #2518 / #2511 |

Removing them from the tuned LightGBM did not measurably change AUC on test_random (-0.0000 [-0.0009, +0.0010]) and did not measurably change it on test_future (-0.0001 [-0.0009, +0.0008]); TPR@1%FPR: +0.0000 [-0.0289, +0.0438] random, -0.0020 [-0.0210, +0.0214] future. The random-minus-future AUC gap is -0.00009 with the proxies and -0.00001 without them (TPR@1%FPR gap +0.0043 vs +0.0063).

So removing the proxies changes the random-minus-future AUC gap by +0.00009: it does not shrink it. 

Reading: if the proxies were a time *leak* that the random split rewards, removing them would cost more on test_random than on test_future and shrink the gap. If the cost is similar on both sets, the model uses them as ordinary file properties (for example, whether a file is signed at all, or has a zeroed or implausible compile date), not as a calendar.

## Why this matters

* A leaked score is not a slightly optimistic score: it measures a different task. With
  `detection_ratio` the model is no longer a detector, it reads the antivirus verdict that the
  label was made from. Deployed, that column does not exist yet when a new file arrives, and the
  model's real performance is unknown.
* AutoML makes this easier to miss, not harder: the search is rewarded for exactly the column a
  human should distrust, and the result arrives as a polished leaderboard with a near-perfect score.
* The date leak is the subtle kind. It looks harmless on its own and its importance can be modest,
  but it is a calendar, not a file property, and a tree cannot extrapolate it past the last training
  date.

## What protects against it

1. **A domain review of feature provenance, before any training.** For every column ask: what is
   it, who produces it, and is it known at the moment the model must decide? `detection_ratio`
   (made by the same AV scans as the label) and `first_submission_date` (a VirusTotal bookkeeping
   time) both fail this test. No tool did this review for us; it has to be a human step.
2. **Temporal validation for time-like leaks.** Training on earlier weeks and testing on later
   ones (our `test_future`) puts every date out of range, so a model cannot use the future dates
   themselves, and a validation score taken that way shows what a date column is really worth
   after deployment. It does not catch post-hoc label proxies such as `detection_ratio`, which
   stay available (and perfect) in every period.
3. **Treat a too-good score as a bug report.** An AUC of 1.0 on malware detection, or one feature
   with most of the total importance, should trigger a look at that feature before anything else.

## Caveats

* One seed and one training sample per run; the CIs cover test-set sampling noise only, not training randomness. Small deltas (around 1e-4 AUC) are within run-to-run variation of the AutoML searches, which are not deterministic in time-budgeted mode.
* The AutoML runs had 30 s each, so their clean scores are not the Step 3 scores; compare each leak run only with the clean run at the same budget.
* Importances are not comparable across tools (gain, permutation, H2O varimp measure different things), so only ranks are compared. H2O's varimp and SHAP come from the best H2O model that has them (a GBM or DRF), which may not be the stacked-ensemble leader. AutoGluon's permutation importance uses its own internal validation rows (a few thousand rows of `train`). Permutation importances can be negative, so a column's share of their sum can exceed 100%.
* `relied_on_leak` is our rule (kept the column and ranked it first), not a statement by the tool.
